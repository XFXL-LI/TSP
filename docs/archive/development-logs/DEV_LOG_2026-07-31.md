# 开发日志（2026-07-31）

## 今日任务

解决设备长时间运行时出现的三类稳定性问题：

1. 屏幕连续查询实时数据后，ESP32 可用堆内存持续下降并最终重启。
2. HJ212 实时上传、历史补传和 CSQ 查询共用串口时可能互相阻塞。
3. pending 文件偶发出现前部全零、无法补传，以及补传任务占用较大瞬时内存。

小时统计的采集、结算和发送规则本次明确不修改。

## 日志分析结论

- 两次重启前，可用堆内存分别从约 23 KB 下降到约 4 KB。
- 异常栈定位到 `DataManager::processQuery()`，原逻辑会为每次屏幕
  `get_data` 复制完整的 `_last_real_snapshot` 映射。
- CSQ 锁忙存在，但当前日志未显示它是实时数据缺失的唯一根因。
- pending 恢复原来会临时创建 5 KiB FreeRTOS 任务，在低内存阶段会进一步
  压缩最大连续内存块。
- pending 文件写入前已经通过协议校验，落盘后却出现大量零字节，符合
  多任务并发访问 FAT/SD 或写后未校验的风险特征。

## 完成的修改（Firmware 2.0.3）

### 屏幕实时查询

- 新增按 ID 读取实时快照的接口。
- `get_data` 改为固定数组和固定 JSON 缓冲区直接返回。
- 删除该命令路径中的临时事件队列、完整 `map` 复制和重复 JSON 解析。
- 最多接受 16 个传感器 ID；响应超限会明确返回失败，不会越界。

### HJ212 串口调度

- 所有 HJ212 命令和上传统一由 `DTUManager` 获取串口锁。
- 实时上传登记等待和发送状态。
- CSQ 查询遇到上传活动时记录 `CSQ_DEFER`，保留上次有效 CSQ，等待下一个
  60 秒周期再查询。
- 保持银尔达 M100M-B2 的逐包发送方式和 1 秒安全间隔。

### pending 补传

- 删除每次补传临时创建的 5 KiB 任务。
- 复用常驻维护任务，每五分钟最多恢复一个 pending 包。
- 因暂时内存不足或源数据不可用而重建失败时保留 marker，后续继续尝试。

### SD 数据完整性

- 增加 SD/FAT 互斥锁，串行化实时保存、历史读取、pending 扫描和补传操作。
- pending 写入完成后重新读取并逐字节比较。
- 校验失败时记录 `PENDING_WRITE_VERIFY_FAIL` 并移除错误文件，避免后续将
  损坏文件当成有效补传数据。

## 测试关注项

- 连续操作屏幕，确认 `GET_DATA_DIRECT` 中的 `free` 与 `largest` 不再持续
  单向下降。
- 上传期间出现 `CSQ_DEFER` 属于正常调度；不应同时出现长时间实时上传停顿。
- 观察 `TX_RESULT ... ack=1`、`RECOVERY_DONE` 和 pending 文件数量变化。
- 不应再出现新生成的前部全零 `.pkt` 文件。
- 对比分钟、小时、日数据文件，确认统计输出规则与 2.0.2 一致。

## Firmware 2.0.4 复测后的调度修正

- pending 扫描仅出现在16:28、16:33、16:38、16:43和16:48。
- 16:48之后连续出现33次 `CSQ_DEFER reason=upload_priority`。CSQ查询和实时
  上传同为60秒周期，延后后继续等待完整60秒会形成相位锁定；依赖成功CSQ的
  pending维护也随之停止，导致两个marker在网络恢复后仍未补传。
- 新增 `CSQ_RETRY_INTERVAL_MS=5000`。只有 CSQ 延后或无效时采用5秒短重试，
  正常健康查询仍保持60秒周期。
- 五分钟 pending 维护在系统取得过一次有效 CSQ 后独立计时。即使当前 CSQ
  被实时上传延后，也会继续按维护周期尝试恢复一个 pending 包。
- 实际补传仍通过 `DTUManager` 仲裁 HJ212 串口，失败时继续保留 marker。
- HJ212逐包间隔继续保持3000毫秒；屏幕、LED实时显示周期、pending文件格式
  以及分钟/小时/日统计逻辑均未修改。
