# Firmware 2.0.6

日期：2026-08-12

状态：单任务OTA内存模型已完成并通过ESP32 Core 3.3.7全量编译；尚未烧录、
尚未触发真实OTA，也未完成硬件专项验证。默认硬件验证发布包仍为Firmware 2.0.4。

## 修改原因

Firmware 2.0.5使用两个OTA任务：开机常驻4KB监听任务，收到合法请求后再动态
创建8KB `otaUpload` worker。2.0.5连续运行约15小时22分钟的实机日志显示，稳定
阶段最大连续内部堆块始终为7668字节。即使总空闲堆仍约14KB，运行中也很可能
无法取得8KB连续块，导致worker创建失败。

Firmware 2.0.4虽然也采用4KB监听加动态8KB worker，但它在创建worker之前直接
删除多个业务任务以释放任务栈。该OTA路径没有实机升级日志，而且强制删除可能
中断持锁、SD写入或串口操作，失败后只能依赖重启恢复，因此不恢复该方案。

## 单任务OTA

- 删除动态`otaUpload` worker和运行时`OtaRequest`堆分配；
- 开机阶段一次创建唯一`OtaUploadTask`，固定栈6KB；
- 同一任务平时以优先级4监听，进入升级会话时把自身提升到优先级11，失败恢复后
  降回优先级4；
- 1KB OTA接收缓冲改为静态缓冲，不再占用OTA任务栈；
- OTA仍通过`BusinessActivityGuard`协作静默业务，不使用`vTaskDelete()`或
  `vTaskSuspend()`强制停止业务任务；
- 先阻止新业务并等待全部在途操作完成，再取得Remote DTU互斥锁，避免OTA持锁
  等待仍需要DTU的在途业务；
- 失败执行`esp_ota_abort()`、释放Remote DTU并恢复业务，不重启设备；
- 只有接收长度完整、`esp_ota_end()`镜像校验成功且启动分区切换成功后才重启。

## 内存诊断

新增`[DIAG] OTA_MEMORY`日志，记录：

- `listener_started`：开机创建单OTA任务后的空闲内部堆、最大连续块和栈高水位；
- `request`：收到合法升级请求时的内存状态；
- `ready`：业务静默、DTU锁定和Flash初始化后的状态；
- `complete`或`failed`：会话结束状态；
- `session_min_free`：Flash写入期间检测到的最低空闲内部堆；
- `stack_high_water`：OTA任务剩余最小栈空间，用于决定6KB是否需要调整。

## 保留的安全边界

- 无数据超时90秒；完整会话上限20分钟；
- 下一OTA分区为空或镜像超过分区容量时拒绝升级；
- 业务静默等待上限90秒，超时则拒绝OTA并继续原业务；
- Remote DTU互斥锁等待上限15秒；
- 传输失败、镜像校验失败或启动分区设置失败均不切换到新固件。

## 固定约束核对

- 小时统计算法未修改；
- HJ212完整报文逐包间隔保持3000ms；
- SHT30代码未修改，继续独立处理；
- `DEBUG`保持开启；
- 2026-08-10完成的采集漂移、秒级校时、RTC优先启动、首次有效CSQ后校时、
  24小时网络校时及HJ212上传优先避让全部保留。

## 当前仍未解决的OTA限制

传输协议仍是800字节原始二进制、分包间隔1000ms，尚未实现分包序号、分包CRC、
应用层ACK和丢包重传。升级后首次启动确认、看门狗自动回滚和固件来源认证也尚未
加入本版本。必须先完成单任务OTA的失败恢复和成功升级实机验证，再继续加入启动
确认与自动回滚。
