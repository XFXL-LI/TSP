# LCD／远程端开关配置协议

适用版本：standard 2.1.3、certified 2.1.3.1。两端使用相同请求、回复和字段含义。
本协议保持LCD已有控件变量和JSON字段名；串口JSON不发送`0x55C0`这类控件地址。

## 控件与兼容字段

| LCD控件地址 | 原显示文字 | 新显示文字 | JSON字段 | true／false含义 |
|---|---|---|---|---|
| `0x55C0` | 温度控制 | 加热控制 | `tempControlSwitch` | 允许原温湿度加热逻辑／强制停止加热 |
| `0x55C1` | 保存数据 | 四区域模式 | `save_raw_data` | 四区域41～44／两区域41、42 |
| `0x55C7` | 远程控制 | LED显示 | `enable_remote_dtu` | 开启／关闭外置LED输出 |

页面轮换与状态查询仍由LCD本地控制。上述两个旧字段仅是协议兼容名称，不控制实际
远程DTU收发或SD实时记录。远程端也必须采用新含义，不能再把它们视为原功能。
所有开关必须发送JSON布尔值，不能发送字符串或数字。

## 查询与保存

查询请求：

```json
{"operation":"get_config","config":"switchConfig"}
```

示例成功回复（实际值以设备为准）：

```json
{"operation":"get_config","code":"OK","config":"switchConfig","content":{"tempControlSwitch":true,"log_to_sd":false,"save_min_data":true,"save_hour_data":false,"save_day_data":false,"enable_hj212":true,"mqtt_public":false,"enable_remote_dtu":true,"save_raw_data":false}}
```

LCD原有八字段保存格式无需改变，只调整显示文字：

```json
{"operation":"set_config","config":"switchConfig","content":{"tempControlSwitch":true,"save_raw_data":true,"log_to_sd":false,"save_min_data":true,"save_hour_data":false,"save_day_data":false,"enable_hj212":true,"enable_remote_dtu":true}}
```

成功回复使用`operation:"set_config"`、`code:"OK"`并回显实际`content`，结构与查询回复
一致。省略的字段保留已存值，例如LCD未发送`mqtt_public`不会删除或改掉该配置。
内容必须是对象；已知开关类型不正确、配置加载／序列化／写入失败时回复`NG`。
保存失败不应用新的运行控制值。`tempConSwitch`作为旧加热字段别名继续接受；
同时出现两个名称时以`tempControlSwitch`为准，回显只用规范名称。

## MCU内部存储与首次升级

LED使用独立的运行状态，不复用原保存或通信业务开关。正常保存时`/switch.json`
写入规范加热字段、原有其他开关及：

```json
{"led":{"enabled":true,"region_count":2}}
```

此结构只用于MCU持久化；LCD／远程端继续使用上面的旧字段，不必发送嵌套`led`。
首次从旧文件启动，没有规范`led`时默认LED开启、两区域；不把旧`save_raw_data`或
`enable_remote_dtu`值误当作用户选择。旧加热配置仍读取并生效。
启动读取不自动改写已有文件；正常`set_config`成功保存后持久化新结构。
升级后LCD应先执行一次查询刷新开关，再由用户保存，避免直接提交升级前遗留控件值。

## LED运行规则

- 每页约5秒连续循环，与120秒采集／上传周期解耦，不在55秒后停止翻页。
- 同页各区域逐帧发送，每帧串口发送完成后至少间隔50ms，再发送下一区域；
  清屏和模式切换也遵守此间隔。每次调度最多发送一帧，间隔通过原LED任务的队列等待
  实现，不在等待期间持有串口锁或OTA业务保护，不新增任务或队列。
- 显示顺序：TSP、PM10、PM2.5、PM1；温度、湿度、气压、风速、风向、噪声；NO2、CO、SO2、O3。
- 只显示最新有效处理批次中存在的因子，紧凑分页，不为分类强制留空页。
  缺少／无效因子沿用跳过行为，不新增“等待数据”或`--`。尚无有效批次／全部无效时
  不发送新数据内容，保留屏幕已有内容；关闭LED仍执行清除。
- 新批次更新最多14条短文本缓存，正常保留轮播游标；缓存缩短到当前页不存在时回到首行。
  LED开关或区域模式改变会重置游标。相同内容和颜色不重复发送。
- 两区域使用41、42；四区域使用41～44。关闭清除四区域，四切二清除43、44，
  最后一页不足的区域清除；清除指令沿用现有协议发送一个空格，串口写失败会重试。
- 待发送区域使用最多4条固定短文本，同页内容在开始发送时复制；新批次到达不会将
  未发送完的一页混成两批。串口写失败保留目标，约5秒后重试；切换模式／关闭时
  取消旧模式未发送内容，但不跳过上一帧的间隔。
- 扬尘场景不含TSP、PM1、噪声，其余11项有效时，两区域6页约30秒，四区域3页约15秒。

上述周期是MCU更新区域寄存器的周期，不是给控制卡发送一组永久循环播放列表。
控制卡自身仍按预设页面／区域和停留时间显示，实际观看节奏需匹配其模板。
串口写入成功不等于控制卡确认接收；空格是否清屏、分帧间隔是否满足实际控制卡须实机确认。
调试日志 `LED_CONFIG` 含 `frame_gap_ms=50`，`LED_TX` 含区域、串口写入结果及
`start_ms/end_ms`。下一帧的 `start_ms` 应至少比上一帧的 `end_ms` 晚50ms
（按无符号毫秒差处理回绕）；`ok=1` 不表示控制卡已回ACK。

## 加热运行规则

`true`仅允许原自动逻辑，不强制通电：温度低于下限或湿度高于上限时启动；
温度达到下限且湿度不高于上限时停止。原阈值及六小时保护保持不变。
`false`在配置保存成功后立即将GPIO42拉低，清除活动标志，并阻止旧判断重新开启。
再次打开后通知现有温控任务，用已有有效温湿度样本恢复判断，无有效样本时不启动加热。
SHT30仍按30秒节奏读取，风扇原逻辑不受加热总开关影响。

温控任务始终创建，使用原4KB任务栈；没有新增LED任务或队列。LED缓存固定大小，
任务只短时处理最新实时包并释放，不在5秒等待期间持有数据包或业务锁。
两版当前ELF静态RAM为28024字节：相对2.1.2系列增加424字节，其中2026-10-09
帧间隔修复比2026-10-08同版本构建增加80字节。LED管理器固定占用416字节，
其中14条主缓存为254字节；不额外分配动态发送队列。相对旧版关闭后不创建温控任务的配置，
还需计入原温控任务栈及RTOS任务开销。实际堆余量以设备日志为准。

## 留待实机验收与后续范围

验收LCD及远程端查询／保存／重启回读、两／四区域循环、少因子尾页清除、关闭LED、
加热进行中关闭及重新开启、关闭加热时SHT30／风扇继续工作、网络及SD业务不受影响。
建议连续运行观察堆余量、任务栈、UART错漏和看门狗。
离线测试和编译不等于硬件验证，当前状态仍为`compiled-not-hardware-verified`。

本轮不重新定义或接通分钟／小时／天数据、日志保存及上传开关的全部业务语义。
不改变采集、气泵、气体重试、HJ212间隔或认证校准策略。LCD程序本身不在本仓库内修改。

离线回归入口为`tools/tests/Run-FirmwareControlTests.ps1`，参数`CxxPath`指向宿主编译器
（本机验证使用Zig 0.13.0），`CjsonRoot`指向cJSON 1.7.19源码目录。
脚本从两版当前正式源码提取实际配置／温控／LED／事件发布实现，仅替换外围依赖，
编译并运行各17组控制测试，包括2万次并发开关关闭测试、9600波特率发送耗时、
帧间隔、发送中切换／关闭、失败重试、批次更新和计时回绕。
`tools/tests/Run-FirmwareReliabilityTests.ps1`另行覆盖原有气体／SD／实时状态回归。
默认测试产物均在被Git忽略的`firmware_workspace/build/`，不会访问设备。
