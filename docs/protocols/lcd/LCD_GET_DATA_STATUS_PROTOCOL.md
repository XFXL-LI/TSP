# LCD 实时数据与设备状态接口整改约定

文档版本：1.1

日期：2026-09-28

扩展结构版本：`ds.v = 1`

适用对象：TSP MCU、LCD 开发人员、使用远程 `get_data` 的云端人员

> 实施状态：standard 2.1.1、certified 2.1.1.1 已实施 MCU 配套修改并编译通过，
> 状态为 `compiled-not-hardware-verified`，尚未完成 LCD/云端及设备实机验收。
> MCU 已维护无有效时间的本地快照并实现可选 `ds`，不修改实验版或 OTA 协议。
> 本文的 LCD 修改和验收清单仍须执行，不能把编译通过描述为显示/硬件验证通过。

## 1. 整改目标与范围

1. 没有网络且时间未校准时，LCD 仍能显示有效的本地测量值，并明确提示时间状态。
2. 区分等待首批数据、有效零值、因子数据无效，不能统一显示成正常零值。
3. 显示 SD 挂载状态和最近写入结果，让用户不必先翻 MCU 日志才能判断是否能够记录。
4. 复用现有 `get_data` 请求和接收处理，不新增长期状态查询定时器或独立查询任务。
5. 保持旧请求、旧回复及 OTA 协议兼容；没有 LCD 不得阻止 MCU 初始化、采集或运行。

本约定不改变因子选择、单位转换、认证专用气体策略、HJ212 格式或 OTA 握手。
正式版采集周期仍为 120 秒、泵运行时序仍为 70 秒；LCD 查询不是触发传感器采集的命令。
本文不是实验版 5 秒采集接口。

## 2. 通道与报文容量

| 项目 | 约定或当前证据 |
| --- | --- |
| LCD 串口 | 9600，8N1，沿用当前连接 |
| 远程控制 DTU 串口 | 115200，8N1；JSON 语义与 LCD 相同，不使用 LCD 波特率 |
| 线格式 | 单行、无缩进的紧凑 JSON，末尾 `\r\n` |
| MCU 当前回复缓冲 | `get_data` 使用 1024 字节字符数组，包含结尾 `\0`，串口另外发送 `\r\n` |
| LCD 拼包保护阈值 | 用户提供截图为 `UART_RX_BUFFER_LIMIT = 1900`，超限保留尾部 512 字节 |
| LCD 硬件接收容量 | 未确认；1900 是 Lua 未解析数据的保护阈值，不是硬件容量证明 |
| 新回复容量限制 | MCU新扩展路径检查完整回复（含 `\r\n`）不超过800字节，超限返回短NG；实际链路仍待验收 |

示例为了阅读可以分行，实际发送不得照搬缩进和多行格式。常规回复只增加短字段、
数字枚举和有效性位图，不重复发送因子名称、单位、配置内容或中文状态文案。

1900 限制涉及累计未解析数据，多条粘包也可能触发。因此 LCD 必须及时解析完整帧，
仅保留剩余半帧，不能只检查单帧长度。LCD 查询应串行处理，同一设备最多一个在途请求。
云端网关如果增加自己的外层封装，还需独立验证封装后的长度，不能直接套用 LCD 阈值。

## 3. 请求与兼容开关

### 3.1 原有请求

```json
{"operation":"get_data","ids":["a34004","a34002"]}
```

未提供 `with_status` 或提供布尔值 `false` 时，新 MCU 仍返回原有字段，不追加 `ds`。

### 3.2 新 LCD 和云端请求

```json
{"operation":"get_data","ids":["a34004","a34002"],"with_status":true}
```

`with_status` 必须为 JSON 布尔值 `true`，不能使用字符串 `"true"` 或数字 `1`。
新 MCU 对此请求追加 `ds.v=1` 状态对象，查询只读取缓存，不触发传感器读取、
SD 挂载、写卡或网络校时。

新扩展路径的 `ids` 约定：0～16 个已知、唯一的因子 ID；超过 16、未知 ID、
重复 ID、非字符串元素或不合法的开关类型应明确返回 `NG`，不能静默截断。
当前空气微站最多启用 14 个非 TVOC 因子，16 是编码位置上限，不是新的因子组合许可。
请求已知但未启用的因子时，保留位置并标记无效；LCD 应优先只请求当前启用的因子。
上述严格输入校验已用于2.1.1系列的新扩展路径；旧路径仍保留原有处理规则。

### 3.3 开机只查状态的可选请求

```json
{"operation":"get_data","ids":[],"with_status":true}
```

回复保留 `params:[]`、`values:[]`，此时 `valid_mask=0`。`seq` 和 `age_ms` 仍描述
MCU 最近的采集批次，不会因为请求列表为空而重置或增加。仅查状态的回复不清除屏幕已有测量值。

也可以在开机后的首条正常数据请求直接携带开关，不必专门增加此空列表请求。
当前串口业务接收任务在配置初始化后启动，早期不保证立即回复；LCD 可以显示
“等待主板初始化”，沿用现有超时和有限重试，不把第一次没有回复等同于硬件故障。
本接口提供当前快照，不保证逐帧重放所有早期初始化步骤。

## 4. 成功回复与字段字典

### 4.1 原有回复示例

```json
{"operation":"get_data","code":"OK","message":"get data success","timestamp":20260928120000,"csq":20,"temp":25.30,"mete":48.00,"params":["a34004","a34002"],"values":[12.00,18.00]}
```

现有字段的名称、类型、单位和精度规则保持不变。`params` 与 `values` 顺序一一对应，
不得删除、改成对象或改变顺序。`code=OK` 仅表示查询成功，不代表时间、SD 或所有因子正常。

`timestamp` 是最近采集批次的 `YYYYMMDDhhmmss` 数值；该批没有有效日期时间时为 `0`。
`csq`、`temp`、`mete` 沿用现有含义；其中 `mete` 是既有湿度字段，不是 SD 容量。
不能只凭 CSQ 数值宣称已连上云端或报文已经送达。

### 4.2 有效测量值但时间未校准

```json
{"operation":"get_data","code":"OK","message":"get data success","timestamp":0,"csq":99,"temp":25.30,"mete":48.00,"params":["a34004","a34002"],"values":[12.00,18.00],"ds":{"v":1,"init":1,"sd":2,"write":0,"time":0,"seq":1,"age_ms":3000,"valid_mask":3}}
```

LCD 显示 PM2.5=12、PM10=18，并提示“时间未校准”；不能因为 `timestamp=0` 拒绝显示。
SD 已挂载，但正式写入尚未发生，不能把 `sd=2` 展示成“数据已记录”。

### 4.3 必选扩展字段

识别到合法 `ds.v=1` 时，下表字段均应存在，类型均为整数。字段顺序不作为解析依据。

| 字段 | 定义 |
| --- | --- |
| `v` | 固定为 `1`，是扩展结构版本，不是固件版本 |
| `init` | `0` 初始化中；`1` 初始化检查结束；`2` 关键初始化失败 |
| `sd` | `0` 未检查；`1` 挂载中；`2` 挂载成功；`3` 挂载失败 |
| `write` | `0` 本次开机尚未尝试正式测量记录写入；`1` 最近一次返回成功；`2` 最近一次返回失败 |
| `time` | `0` 当前系统时间无效；`1` 当前有效时间由 RTC 初始化；`2` 当前有效时间已经网络校准 |
| `seq` | 本次开机采集批次序号，范围 0～4294967295；0 表示尚无批次，有批次时非零 |
| `age_ms` | 最近批次距今的毫秒数；尚无批次时为 -1，否则为 0～4294967295 |
| `valid_mask` | 0～65535 的有效性位图，bit0 对应 `params[1]`（Lua 下标）；只使用本次回复的因子位置 |

`init=1` 表示必要初始化检查结束，不表示 SD、时间和网络全部成功；非关键异常仍可进入
带告警的运行状态。`init=2` 应显示关键初始化故障，不要求 MCU 等待屏幕确认。

MCU在启动主流程和首次RTC检查均完成后退出 `init=0`，不等待DTU连网或LCD确认。
已检测的配置/FFat加载失败、业务任务创建失败、DataManager/存储互斥锁或队列失败、
泵保护定时器创建失败会置为 `init=2`，本次启动内保留此故障状态；这不是全部硬件自检。

`time` 描述当前系统时钟，`timestamp` 描述本批数据，两者不能混用。网络校时刚成功时，
可能出现 `time=2`、`seq>0` 但 `timestamp=0`：上一批仍没有日期，下一批才携带有效日期。
不能给旧批次补造时间。`time=1` 也不是 RTC 硬件完整自检或真实日期正确性的证明。

`write` 仅描述正式测量记录的最近写入返回结果；不代表所有文件已经通过读回/CRC 校验，
不覆盖 HJ212 pending 独立验证状态，也不表示历史缺失已经补齐。时间未校准而暂停记录时，
即使 SD 挂载正常也不能显示“正在正常记录”。

`seq` 只在采集批次更新时变化，查询不会使它变化。序号回绕时跳过 0；LCD 不得依赖
序号永远递增。`age_ms` 使用单调运行计时，不随 RTC 校时跳变，超出范围时饱和到上限。
MCU 重启、LCD 实际重连或首次处理恢复通知后，LCD 清空旧采集和日期基准；重复 OTA
`normal` 消息仍按原协议去重，不反复重启恢复定时器。

### 4.4 可选故障字段

`sd_error` 为有符号 32 位整数，仅在 `sd=3` 且有已知底层挂载错误码时追加：

```json
{"operation":"get_data","code":"OK","message":"get data success","timestamp":20260928120000,"csq":99,"temp":25.30,"mete":48.00,"params":["a34004","a34002"],"values":[12.00,18.00],"ds":{"v":1,"init":1,"sd":3,"write":0,"time":1,"seq":1,"age_ms":3000,"valid_mask":3,"sd_error":-1}}
```

`-1` 仅为报文示例，不是本设备实测错误。LCD 显示“SD 挂载失败，错误码 -1”，
不得凭一个错误码断言 MCU、SD 卡或接线中的某一项必然损坏。`sd=3` 但字段缺失时，
显示“SD 挂载失败，具体错误码未提供”，不能默认成成功。
挂载状态恢复后 MCU 省略该字段，LCD 清除旧的当前故障码显示。正常回复不携带长错误文案。

`sd` 描述最近挂载检查，并非持续卡在位检测；本轮未增加热插拔探测或自动重挂载。
记录写入会检查实际写入数量及关闭结果。写入开关关闭、无有效时间或SD未挂载而跳过时，
不会伪造一次成功写入，`write` 保留最近实际写入尝试的结果。

## 5. 有效性位图与数据显示

有效性位图按本次回复顺序映射，不使用固定因子编号：

| `params` 项数 | `valid_mask` | 含义 |
| --- | ---: | --- |
| 2 | 3（二进制 11） | 两项都有效 |
| 2 | 2（二进制 10） | 第一项无效，第二项有效 |
| 2 | 0 | 两项都无效；是否已经采集要另看 `seq` |
| 14 | 16383 | 14 项都有效 |
| 0 | 0 | 没有请求因子，不表示设备所有传感器无效 |

`valid_mask` 对于 N 项因子只能使用低 N 位，N=0 时必须为 0。
无效位置的 `values` 保留数字 0 作为兼容占位，不能解释为测量零值。
有效位置的 0 则必须作为真实零值显示。位图只表达能否使用，不区分未启用、通信失败、
传感器状态异常、维护或标定；LCD 不得统一将 bit=0 显示为“硬件损坏”。

Lua 判定位示例（前提：已经验证 `ds.v=1`、字段类型、范围及数组对应关系）：

```lua
for i, id in ipairs(response.params) do
    local valid = math.floor(response.ds.valid_mask / (2 ^ (i - 1))) % 2 == 1
    if response.ds.seq == 0 then
        -- 显示“等待首批数据”，不把占位 0 当成测量值。
    elseif valid then
        -- 显示 response.values[i]，不以 timestamp 非零作为显示前提。
    else
        -- 显示“--”或“数据无效”，不显示成正常零值。
    end
end
```

尚无采集批次的例子：

```json
{"operation":"get_data","code":"OK","message":"get data success","timestamp":0,"csq":99,"temp":25.30,"mete":48.00,"params":["a34004","a34002"],"values":[0.00,0.00],"ds":{"v":1,"init":1,"sd":2,"write":0,"time":1,"seq":0,"age_ms":-1,"valid_mask":0}}
```

第一项无效、第二项有效的例子：

```json
{"operation":"get_data","code":"OK","message":"get data success","timestamp":20260928120200,"csq":20,"temp":25.30,"mete":48.00,"params":["a34004","a34002"],"values":[0.00,18.00],"ds":{"v":1,"init":1,"sd":2,"write":1,"time":1,"seq":2,"age_ms":3000,"valid_mask":2}}
```

每次合法回复都更新 SD、时间和年龄显示，即使 `seq` 没有变化；同一批期间也可能发生
网络校时或写卡结果变化。数据是否陈旧应结合 `age_ms`，不能把每次查询返回当成新采集。
沿用 LCD 既有、与 `collect_time` 相匹配的新鲜度策略；若原先仅靠日期差判断，应改用
`age_ms`，具体陈旧阈值在联调中确认，不在本接口中新增一个固定的 5 秒规则。
无回复时保留上次值也必须标记通信中断/陈旧，不能继续宣称状态实时正常。

## 6. LCD 开机、运行与历史同步整改

1. 开机复用现有串行请求队列，在首条合适的 `get_data` 加上 `with_status:true`；
   可使用空列表或当前显示因子列表，不新增独立长期定时器。
2. 等待回复期间显示“等待主板初始化”；超时沿用现有有限重试和通信提示。
3. `init=0` 显示初始化中；`init=1` 进入带状态提示的正常页面，不等待 SD、时间、网络全部成功；
   `seq=0` 另外提示“等待首批数据”。`init=2` 显示关键故障并允许必要的设置/诊断操作。
4. 运行中继续原来的 `get_data` 查询节奏并携带开关，不额外轮询状态，不自动改变采集周期。
5. 时间无效时有效测量值照常显示；SD 异常时提示记录不可用，但不能因此禁止实时显示。
6. 只有配置周期已经确认、当前系统时间有效且本批 `timestamp` 有效时，才允许建立 raw
   缺失判断、小时/天历史同步的日期基准。未满足条件时暂停这些功能，不补查 1970 年记录。
7. 时间从无效恢复后，清空旧日期基准，从下一条带有效日期的采集批次重新开始判断。
   不因重复查询同一批而重复补缺失，不把无日期数据归入正式历史。
8. 保持已有登录、systemConfig 与因子 selection 的初始化顺序及配置权限规则；不要为了
   查询状态打乱在途配置请求。只读 `get_data` 沿用现有访问方式，不新增写入权限。
9. 保持 OTA 优先级：升级期间仍按现有协议暂停普通查询，收到恢复通知后按既有规则恢复。
   `ds.init` 不替代 `ota_status`，也不新增状态 ACK。

## 7. 旧版兼容和错误回复

| 配合情况 | LCD/云端处理 |
| --- | --- |
| 旧 LCD + 新 MCU | 没有开关，返回旧字段结构；旧屏对无效时间是否显示仍取决于其原有逻辑 |
| 新 LCD + 当前旧 MCU | 当前 2.1.0/2.1.0.1 会忽略未知开关并返回旧结构；没有 `ds` 时按旧接口处理，状态显示“未提供” |
| 新 LCD + 新 MCU | 验证 `ds.v=1` 后启用本文显示与日期保护逻辑 |
| 新 LCD + 未知 `ds.v` | 不按版本 1 强行解释，状态显示“不支持的状态版本”，数据回退既有处理 |

未返回 `ds` 不能用默认零值补成 `sd=0/time=0` 并宣称设备异常。更早历史 MCU 的兼容性
仍需联测。未知扩展字段可忽略；识别到 v=1 但缺少必选字段、类型/范围错误或数组不对应时，
应提示状态/报文异常，不将无法验证的占位零展示为可靠测量结果。

正常回复必须是完整、合法 JSON；不得输出 `NaN`/`Inf`。新路径输入错误或容量超限时，
使用短 `NG` 回复，不能截断 JSON、静默截断请求因子或发送半包。拟定错误例子：

```json
{"operation":"get_data","code":"NG","message":"Response too large"}
```

```json
{"operation":"get_data","code":"NG","message":"Too many requested ids"}
```

快照暂时繁忙仍可沿用当前回复：

```json
{"operation":"get_data","code":"NG","message":"Data snapshot busy"}
```

客户端收到 `NG` 不把占位值覆盖到实时页面，按既有错误处理显示状态。
若后续确需把多因子查询分组，应作为明确的后备策略并核对每组 `seq` 一致，不能默认
增加分包流程或拼接不同批次。网络包装、请求关联由现有串行事务管理负责，MCU 未新增 request ID。

## 8. MCU 配套实现与联调边界

以下条件已落实到MCU源码；编译不替代实机验收：

- 无有效日期时仍读取传感器并更新本地实时快照；只加回复字段无法解除当前数据发布限制。
- 最新测量快照与带日期的存储/统计/HJ212 分开；时间无效时不生成伪日期记录，不使用
  编译时间伪装已校准，也不把无日期积压无限保存在内存。
- 同步检查当前硬编码日期门槛，采用一致的有效时间规则，避免合法 RTC 日期被不同模块拒绝。
- `params`、`values`、`valid_mask`、`seq`、`timestamp`、`age_ms` 从同一批受保护快照取得，
  避免并发更新造成值与位图错位；保持低分配查询方式，不为每次请求克隆完整因子 map。
- SD/时间状态由 MCU 自主维护，查询仅拷贝快照；不新建大栈状态任务，不把 SD 操作或
  网络查询放入 `get_data`。无屏、屏幕无回复和屏幕晚启动均不影响 MCU 工作。
- 两个正式变体同步公共修改；认证专用策略保持隔离，不修改实验版本。

## 9. 容量预算与验收清单

以下是按紧凑 ASCII JSON 和示例值核算的长度，不是设备实测，也不是合法数据的最大值：

| 示例 | 长度，包含 `\r\n` |
| --- | ---: |
| 14 因子旧结构 | 359 字节 |
| 同一示例追加精简 `ds`，采用 `age_ms/valid_mask` | 448 字节 |
| 同一示例全部值使用 `1000000000.00` 的宽度，追加 `ds` | 559 字节 |

`sd_error`、最大序号/年龄、负数、单位变化及更长数值还会增加长度；不能只凭 14 项数量
保证不超限。实现须验证输入 ID、数字有限性、实际序列化长度和 MCU/LCD 两端容量。
常规扩展目标为完整回复不超过 800 字节；无法满足时完整返回短 `NG`，不扩大缓冲来
掩盖异常输出。正常合法量程能否全部满足目标，需要在实现时按当前转换和输出规则验证。

联调至少覆盖：

1. 无网、RTC 时间无效：取得有效测量值，LCD 显示数值和时间未校准提示，不补虚假历史。
2. 无网、RTC 正常、SD 正常：保持采集，正常记录；CSQ 不作为本地显示的前提。
3. SD 挂载失败：继续显示测量值，正确显示失败和可选错误码；恢复后不残留当前故障码。
4. 挂载正常但正式写入失败：`sd=2/write=2`，不能错误显示记录正常。
5. 未采集、真实零值、单因子无效、整批无效分别显示正确。
6. 网络校时完成但旧批次仍 `timestamp=0`：不补造时间，从后续有效日期批次建立基准。
7. 14 因子完整读取、部分关闭、TVOC 单因子、16 位置边界及非法 17 项输入。
8. 数值宽度、负数、各合法单位、非有限/异常值和最大元数据；记录实际最大回复字节数。
9. LCD 分包、粘包、延迟处理及查询超时；验证 1900 拼包保护不会导致合法回复被丢弃。
10. 旧请求、缺失/未知扩展版本、畸形 v=1 回复、MCU 重启和 OTA 恢复均处理正确。
11. 不接 LCD、运行中拔掉 LCD、晚接 LCD：MCU 持续运行，接入后能查询当前状态。
12. 远程 `get_data` 与 LCD 的字段和位图语义一致，HJ212 和 OTA 报文没有被扩展或改写。
